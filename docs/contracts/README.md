# Cross-client contracts

Vibe Bar ships as two clients — this macOS app and Vibe Bar Desktop —
and these files are what keep them one product rather than two that
resemble each other. Each is generated from this repository, because
this app is the reference implementation, and each is checked here so a
change fails in the repository that caused it.

Vibe Bar Desktop vendors its own copy of each file and checks it against
its own implementation. That copy is updated by hand, so a change here
is not finished until it has been carried across.

| File | Covers | Checked by |
| --- | --- | --- |
| `design-tokens-v1.json` | Provider accents, quota-bar colours and thresholds, card recipe | `DesignTokenContractTests` |
| `quota-naming-v1.json` | The quota axis: L1 company, L2 SubProvider, L3 group, and the rules that assign them | `QuotaNamingContractTests` |
| `forecast-v1.json` | The quota pace forecast, as evaluated vectors | `ForecastContractTests` |

## `design-tokens-v1.json`

Generated from `Theme.swift`. A provider that is teal in one client and
green in the other is two providers as far as the reader is concerned,
so the test binds every value back to its declaration in the theme.

## `quota-naming-v1.json`

Generated by `Scripts/generate_quota_naming_contract.py` from
`ProviderHierarchy.swift`, `MiniWindowGroupLabelCatalog.swift` and
`QuotaFieldRegistry.swift`. The main test re-runs the generator and
diffs, so it covers rules added after the test was written.

Note what the tables alone cannot tell a second implementation, and why
`groupKeyOrder` and `branchStyle` are in the file: whether a bucket is
an L3 group of its own at all, and in what order the rules apply.

## `forecast-v1.json`

Each case is evaluated at 25%, 50%, 75% and 95% of its window, and both
clients must agree on every field — verdicts and confidences exactly,
numbers to 1e-6. A gap smaller than a reader could see still means the
two implementations have started to diverge.

Cases whose input carries `completedCycles` exercise the historical
projection, which the first five leave untouched. They also encode two
decisions that were got wrong once: a cycle's stored `windowStart` is
used as it stands rather than reconstructed from the nominal window
(many buckets refill far more often than the window they advertise, so a
short span is usually the truth), and the observation stamped at a
cycle's end belongs to the cycle that follows.

Regenerate the cycle-carrying cases with:

```sh
VIBEBAR_EMIT_FORECAST_VECTORS=/tmp/cycles.json swift test --filter ForecastVectorGenerator
```
